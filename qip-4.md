# QIP 4, Transaction Format and Signature Envelope

## Abstract

This proposal documents the Quantova transaction format and the signature envelope that authorises it. One shape carries every account action on the network, from a plain value transfer to a contract call. A transaction is a body of typed fields wrapped in an envelope that holds a scheme identifier and a post quantum signature. The body names the sender, the nonce, the meter limit, the fee, the call to make, the value carried with that call, and the chain id. The signature is computed over a fixed encoding of the body under a domain tag, and the default scheme is ML-DSA-65. A native transfer is not a separate object, it is a call whose arguments encode the amount, so one encoding and one signing rule cover the whole surface. This is a foundational design of the network and is recorded here as a Final Core document.

## Motivation

Every account action needs one canonical shape so that a signer, a gateway, and a validator agree exactly on what was authorised. If the bytes a wallet signs are not the bytes a validator checks, an action can be replayed, reshaped, or repudiated. Quantova fixes the shape once. The body is encoded into a deterministic byte string, a domain tag is appended, the result is hashed with SHA3-256, and that digest is signed with a post quantum scheme. Because the chain id is one of the signed fields, a signature made for one Quantova network does not authenticate the same body on another, which closes cross network replay. Because a value transfer is a special case of a call rather than its own message type, there is a single code path, a single encoding, and a single signing rule for transfers, contract calls, and payable calls alike. The whole authorisation path is post quantum so that neither a classical nor a quantum adversary can forge a transaction.

## Specification

The transaction body is the `Body` structure in the `qtv-tx` crate. It carries the sender address, the `nonce`, the `meter_limit`, the `fee`, a `Call`, the `value`, and the `chain_id`. The `Call` in turn holds a target address and a byte string of arguments. When the body is encoded, each address is first reduced to its raw 32 byte payload and written with an eight byte little endian length prefix in front of it. The `nonce`, the `meter_limit`, the `value`, and the `chain_id` are each written as eight byte little endian integers. The `fee` is a wider quantity and is written as a sixteen byte little endian integer. The encoded order is the sender, the `nonce`, the `meter_limit`, the `fee`, the call target and its argument bytes, the `value`, and then the `chain_id`. This encoding is deterministic, so the same body always produces the same bytes.

A native transfer is a call that encodes the amount. The transfer helper writes the amount as an eight byte little endian integer, uses those bytes as the call arguments, sets the target to the recipient address, sets the meter to the fixed native transfer budget, and then signs it exactly as any other call. The bytes and the transaction id of a transfer are identical to the bytes and id of the equivalent call built by hand with the same amount encoded into its arguments. The separate `value` field carries funds attached to a call, so a payable call moves a nonzero `value` into the body and a plain call leaves it at zero. The two are distinct, the transfer amount lives in the call arguments and the payable amount lives in the `value` field, and both are inside the signed body.

The `meter_limit` is the execution budget the sender grants to the transaction. It is a meter, an upper bound on the execution work the transaction may consume, and it is not a fee. A native transfer sets this budget to the fixed native transfer meter constant. The `fee` is a separate field, the amount the sender pays for inclusion, denominated in the network base unit reported by the node as its denomination. In the client bindings the fee a sender signs is bounded by the sender, the client reads the fee the gateway quotes and refuses to sign when that quote is above the maximum the caller stated, so a gateway cannot inflate the fee on a plaintext request.

The signature envelope is the `Wrapper` structure. It holds the body, a one byte scheme identifier, and the signature bytes. Signing first builds the body digest, which is SHA3-256 over the encoded body with the domain tag `quantova.transaction.v1` appended. The signer selects the scheme from the account and produces a signature over that digest. The default scheme is ML-DSA-65, the lattice scheme identified by the scheme byte value one, standardised as ML-DSA-65 under FIPS 204. A hash based SLH-DSA scheme is selectable under the scheme byte value two. A third slot is reserved for the FN-DSA scheme and is gated until that standard is final. Every scheme on this path is post quantum. Verification recomputes the body digest from the wrapped body, reads the scheme byte, and checks the signature against the supplied public key under that scheme, so the signature stands over the digest of the exact body it travels with.

The ML-DSA-65 signature binds the whole body. The digest it signs is taken over every encoded field, so any change to the sender, the nonce, the meter limit, the fee, the call target, the arguments, the value, or the chain id moves the digest and the signature no longer verifies. Since addresses are bound as their decoded 32 byte payloads rather than as their rendered strings, the casing of an address cannot change the signature, and an address that does not parse to a payload is refused at signing time rather than being silently encoded as empty. The signer fails closed on an unparseable sender or an unparseable call target.

The transaction id is SHA3-256 over the entire encoded wrapper, which is the body, the scheme byte, and the signature together, rendered as a Bech32m string under the transaction human readable part so that it begins `QTX1`. Because the id covers the signature as well as the body, two wrappers that differ in any field or in the signature carry different ids, and an id round trips through its rendered form.

The chain id is folded into the signature by being a field of the signed body. The chain id of a network is derived from its display name by hashing the name with SHA3-256 and taking the leading eight bytes as a big endian integer, giving a sixty four bit identifier. The network names are `Q-dev-net-1` for the local development network, `Q3` for the testnet, and `Q1` for mainnet, each with its fixed chain id constant. A signature produced for one chain id does not verify against the same body carrying a different chain id, so a transaction signed for one Quantova network cannot be replayed onto another.

## Rationale

Binding addresses as their raw payloads rather than as text means the signature is over the identity itself and cannot be shifted by casing or by a rendering choice, which removes a whole class of ambiguity between what a wallet showed and what a validator checked. Appending the `quantova.transaction.v1` domain tag before hashing separates a transaction digest from any other message that might share the same bytes, so a signature over a transaction body cannot be lifted into another context. Placing the chain id inside the signed body, rather than checking it out of band, makes cross network replay a signature failure rather than a policy rule that a relay could forget to apply. Expressing a native transfer as a call means there is one encoding and one signing rule to reason about and to audit, instead of a separate transfer path that could drift from the call path. Carrying the scheme as a one byte identifier in the envelope keeps the format agile across post quantum signature schemes without changing the body encoding, so a future scheme is a new identifier rather than a new transaction format. Keeping the meter and the fee as separate fields draws a clean line between the execution budget the sender grants and the amount the sender pays.

## Backward Compatibility

This is the transaction format of the network from genesis, so there is no earlier deployment to remain compatible with. The domain tag carries the explicit version marker `quantova.transaction.v1`, and the scheme byte reserves room for further post quantum signature schemes to be added without changing the body encoding. A change to the field set or to the encoding would be a new version of the domain tag and a new document.

## Security Considerations

The signature binds every field of the body, including the chain id, and verification recomputes the digest from the wrapped body, so a tampered body, a tampered nonce, a tampered signature, a mismatched public key, or an unknown scheme byte are each rejected rather than accepted. The signer fails closed when the sender or the call target does not parse to an address payload, which prevents a signature from ever standing over a body that silently dropped an address. The domain tag gives domain separation so a transaction signature cannot be reused as a signature over an unrelated message. In the client bindings the fee is bounded by the signer, which stops a gateway from raising the fee on a plaintext submission beyond what the sender allowed. The chain id is a sixty four bit value taken from the leading eight bytes of the SHA3-256 of the network name, and its role here is network separation of signatures. Quantova is on testnet, and external audits of the transaction format and of its post quantum cryptography are still ahead. This document describes the format and its intended properties.

## Test Cases and Reference Implementation

The reference implementation is the `qtv-tx` crate of the Quantova chain, which defines `Body`, `Call`, and `Wrapper` together with the `sign` and `verify` functions, and the client side bindings in the QCore.rs library, which build transfers, calls, and payable calls over that crate. The test suite pins the behaviour described here. A transfer is shown to be byte identical to the equivalent call that encodes the amount into its arguments. A payable call is shown to bind the value into the signature, since a funded call and a free call over the same target differ in both their bytes and their id. Tampering with the body, the nonce, or the signature, and presenting a mismatched public key or an unknown scheme, are each shown to fail verification. A signature made for mainnet is shown not to verify against the same body carrying the testnet chain id. The transaction id is shown to begin `QTX1` and to round trip through its rendered form. Cross language conformance vectors are pinned in the suite, including a fixed transfer body encoding and a payable transaction whose transaction id is fixed, so that the client bindings and the chain agree byte for byte. These tests run on the public testnet build.
